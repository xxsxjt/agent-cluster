# 02 — 分身高可用（HA）方案设计稿

> 状态：讨论稿（只设计，不实装）
> 作者：night-worker · 2026-08-05
> 触发：用户睡前口述的"互备监视"思路，要求评估并给出更优解
> 参考现状：`butler.js` 巡检循环 15s（`POLL_MS=15000`，`checkActive()` 只查 DONE 标记与进程存活）；`lib/spawn.js` pi 分支协议（`pi --mode rpc --session-dir <agents/xxx/sessions>`，3 秒后 stdin 发 `{type:'prompt',...}`）；分身 = twin 节点（user-twin 人格 v3.1，org.json 中 `onlinePolicy: always`）

---

## 0. 先把问题定义清楚

"分身 HA"要保的是什么？**保"活"，不保"窗口"。**

- **活（task/work）**：正在执行的任务、决策职责、监视职责。其真相全部在文件系统里——`inbox/*.md`、`*.DONE/*.PID`、`agents/<id>/tasks/`、checkpoint 文件。进程死了，活的状态不丢，换个进程接着干即可。
- **窗口（interactive session）**：用户正在对话的那个交互窗口。**这个无法后台恢复**——它是活在人面前的会话，进程一死窗口即消失。接管者能做的是：读文件系统里的现场（任务进度、最近摘要），给用户留一句"1号掉了，我已接手，当前进度是 X"。

由此推出 HA 的两条主线：

1. **任务线**：掉线 → 重启恢复（session 恢复上下文）→ 重启失败 → 换人接手，从文件系统重建现场。
2. **交互线**：主分身窗口掉线 → 备用分身转正 → 主动告知用户现场摘要，等用户重新开口。

任何方案都要分别回答这两条线怎么处理。

## 1. 用户原案分析：互备监视环

### 1.1 原案还原

> 1号干活时定期看2号（备用）还在不在；2号发呆时也定期看1号；1号掉了，2号先尝试激活1号，激活不了就启动3号（接替2号的监视职责），2号去接管1号的任务。

抽象成拓扑：**环形互盯**——每个实例监视下一个，干活者被发呆者监视，接管时监视职责顺延给新拉起的那个。

### 1.2 优点（值得保留的思想）

| 优点 | 说明 |
|---|---|
| 去中心化 | 没有单点仲裁者，不依赖 butler 存活 |
| 贴近直觉 | 同事互相照应，符合"组织里的人互相看着"的隐喻 |
| 接管者天然知情 | 2号一直在盯1号，对1号的状态有持续感知 |

### 1.3 隐患

1. **谁看看守者（quis custodiet）**：2号盯1号时，2号自己挂了怎么办？原案靠3号接替，但"接替动作"本身由谁触发？环形结构里每一环的失效都要靠上一环发现，而上一环可能正在干活/也在掉线边缘。**监视链的最后一环永远无人监视**。
2. **互盯开销摊在干活者身上**：1号在干活还要定期探2号，等于每个工作者自带一份监工税；分身越多，探活流量 O(n)。
3. **接管链混乱 / 脑裂**：1号只是模型响应慢（夜间 qwen 排队很常见），2号误判死亡→激活3号+自己接管→1号缓过来→**两个1号同时在跑同一任务**。环状协议里没有仲裁者裁决"到底谁算活着"，脑裂要靠约定（如文件锁）硬凑。
4. **职责抖动**：2号接管1号任务的同时，还要把监视职责移交给3号——一次故障触发两次角色变更，状态机复杂，中间态多（2号"正在接管但还没交接监视"时它自己挂了，全盘失控）。
5. **上下文断层**：2号接管1号任务时，1号的会话上下文在1号的进程/session 里，2号只能从文件系统重建现场——这点和哪套方案无关，但原案没有指明重建机制。

**结论**：原案的"去中心化互备"思想可取，但把**探活**、**仲裁**、**接管**三种职责混在同一批节点上，导致监视盲区、脑裂风险和状态机复杂度同时上升。拆职责即可化解。

## 2. 分身建议案：管家仲裁制（推荐）

### 2.1 核心思路

把三种职责拆开：

- **探活**：分身只负责写心跳（几乎零成本，一次文件写入）；
- **仲裁**：butler（管家 COO）独占"谁活着、谁该重启、谁该转正"的裁决权——它是现成的常驻巡检者，15 秒一轮，加一个心跳检查是顺手的事；
- **接管**：备用分身池平时休眠（零成本），butler 判定需要时才拉起。

这等于把用户的"环形互盯"改成"**星型仲裁**"：分身不互相看，butler 看所有人。原案担心的"监视者自己挂了"问题，转移为"butler 自己挂了"问题——而 butler 是单一、无状态、职责简单的进程，用 OS 级看门狗兜底比用另一个智能体兜底便宜得多（见 2.5）。

### 2.2 心跳机制

每个活跃分身实例定期写：

```jsonc
// org/heartbeats/twin-<n>.json
{
  "id": "twin-1",            // 实例 id（池内编号）
  "role": "primary",         // primary | standby
  "ts": "2026-08-05T02:00:00Z",  // 最后心跳时间
  "pid": 12345,
  "currentTask": "inbox/xxx.md",  // 当前任务（无则 null）
  "sessionId": "sess-abc",        // pi/claude session id，供恢复用
  "sessionDir": "agents/twin/sessions",
  "note": "可选：一句话说正在干嘛（供接管者读）"
}
```

写入时机：**每轮工具调用后**或**每 30 秒**（取先到者）——由分身进程内的轻量 hook 完成。长思考（模型推理中）也要有心跳：推理期间由进程侧定时器写，不依赖模型响应。

### 2.3 butler 巡检逻辑（改动点预告，不实装）

在 `butler.js` 的 `cycle()` 里加 `checkHeartbeats()`：

```
每轮（15s）：
  for each hb in org/heartbeats/*.json:
    age = now - hb.ts
    if age < TIMEOUT:                 continue        # 活着
    if age < TIMEOUT*2:               标记 suspect，下轮再看（防抖，治"模型排队慢"）
    else:                             触发恢复流程（见 2.4）
```

- `TIMEOUT` 建议 90s（= 3 个巡检周期 + 心跳间隔余量），**待用户裁决**（分歧点 D4）。
- 两次确认才判死（防抖），避免把一次磁盘卡顿误判成死亡。

### 2.4 恢复流程（接管伪代码）

```
function recover(dead):                    # dead = 超时的心跳记录
  log 事件到 logs/ha.log
  if dead.role == 'standby':               # 备用掉了：直接静默补一个新的
      spawnStandby(); return

  # 主分身掉了
  attempt 1..2:                            # 先原地重启（保上下文）
      child = spawnAgent({ type, prompt: RESUME_PROMPT,
                           sessionDir: dead.sessionDir, resume: dead.sessionId })
      wait 60s for new heartbeat
      if 收到心跳: return                  # 复活成功，任务/窗口职责原地接续

  # 重启失败 → 备用转正
  promote(standby):
      standby.role = 'primary'
      给 standby 发接管 prompt：
        "你接管 twin-1 的职责。现场材料：
         - 任务进度：agents/twin/tasks/、inbox/ 未完成项
         - 1号最后状态：heartbeats/twin-1.json 的 note
         请生成一段给用户的摘要：当前在做什么、进度、预计影响。"
  spawnStandby()                           # 补一个新备用，池子回到满编

  if dead 有 currentTask:                  # 任务线：从文件系统重建
      任务文件仍在 inbox/（无 .DONE）→ butler 天然会在下轮重新派发
      → 派给转正后的分身，携带原 sessionId 做 --resume 尝试续上下文
```

关键论断（也是全案的支点）：

> **任务状态的真相在文件系统（inbox / tasks / checkpoint），会话连续性靠 session 恢复（pi/claude 的 session-dir + resume）。所以 HA 保的是"活"不是"窗口"——交互窗口无法后台恢复，接管者读文件系统重建现场，给用户留摘要。**

这正好与现状无缝衔接：butler 的 `scanInbox()` 本来就只重派"无 .DONE 的 .md"，掉线进程没写 DONE 的任务**自动进入重派队列**，几乎不用新代码。

### 2.5 butler 自己挂了怎么办（原案隐患的正解）

原案"监视者自己挂了谁管"在本方案里收敛为一个简单问题：**看门狗看 butler**。

- butler 无模型依赖、无上下文、职责单一，挂了重启无损失（状态全在文件系统）；
- 用 OS 级看门狗：Windows 任务计划程序每 5 分钟跑一次 `butler-check`（读 `butler.pid` → `process.kill(pid,0)` 探活 → 不在就 `cscript start-butler.vbs`）；或把 `start-butler.vbs` 改成带重试循环的守护脚本；
- 分身心跳文件同时是 butler 的间接证据：butler 若停止巡检，备用方案可让**主分身**发现"butler 心跳"（butler 每轮顺手写 `heartbeats/butler.json`）超时 → 主分身执行 `cscript start-butler.vbs`。这是原案"互盯"思想的唯一保留处：只保留一条边（主分身→butler），不成环。

### 2.6 备用分身池

- `org.json` 增加 `twinPool: { size: 1, members: ["twin-standby-1"] }`（池大小默认 1，**待裁决**，分歧点 D1）；
- 备用平时 `status: sleeping`，**不启动进程、不消耗 token**，只在 org.json 里占一个节点；
- 备用与主分身共用 `agents/twin/` 目录（人格 = user-twin v3.1 SKILL.md，全继承原则下备用天然具备同样的思维），但各自独立 session-dir，避免会话互踩；
- 转正后旧 id 保留在 `logs/ha.log` 做审计。

## 3. 对比结论

| 维度 | 原案：互备监视环 | 建议案：管家仲裁制 |
|---|---|---|
| 复杂度 | 高：角色状态机（干活/发呆/接管中/移交监视）× N 实例，交接中间态多 | 低：写心跳 + 一个巡检函数，复用现有 cycle |
| 可靠性 | 监视链最后一环无人监视；误判慢实例→脑裂（双1号） | 单一仲裁者防抖两次确认；脑裂由 butler 独占裁决权杜绝 |
| 开销 | 每个干活者带监工税，探活 O(n) | 心跳=每30s一次文件写，巡检=每15s读几个小 JSON，可忽略 |
| 单点风险 | 无中心，但每环都是隐性单点 | butler 是单点 → 用 OS 看门狗 + butler 心跳兜底（见 2.5） |
| 接管上下文 | 未定义，靠接管者自行摸索 | 明确：session resume 优先，文件系统重建兜底，给用户留摘要 |
| 与现状契合 | 需全新实现互盯协议 | scanInbox 重派逻辑天然复用，改动集中在 butler.js 一处 |
| 扩展性 | 加实例→环变长→交接更乱 | 加实例→多一个心跳文件，池化管理 |

**推荐：管家仲裁制（方案 B）**。理由一句话：**把探活做成零成本的写文件，把仲裁交给本来就常驻巡检的 butler，把接管交给文件系统真相——用职责分离消掉原案的脑裂与监视盲区，复杂度反而更低。**

### 第三案（备选，不推荐为主案）

**纯 OS 看门狗制**：完全不依赖 butler，用任务计划程序直接监控每个分身进程（按 PID/窗口标题），掉线直接按预置命令重启。优点是最简单、连 butler 都不信；缺点是没有"仲裁智能"——无法做"重启失败→备用转正→生成给用户的摘要"这类需要判断力的动作，只能无脑重启，交互线完全失守。**适合当 B 案的兜底层，不适合单独成案。**

## 4. 实装拆解（供后续任务使用）

### 4.1 心跳格式与目录

- 新增 `org/heartbeats/` 目录；文件 `twin-<n>.json`、`butler.json`，schema 见 2.2；
- 写入方：分身进程内 hook（每轮工具调用后 + 30s 定时器双触发）；butler 每轮 cycle 写 `butler.json`；
- 清理策略：进程正常退出时删自己的心跳；butler 每天清一次超过 24h 的陈旧心跳。

### 4.2 butler.js 改动点清单

1. 新增 `checkHeartbeats()`：读 heartbeats 目录 → 防抖判死（suspect 一轮 → dead 一轮）→ 调 `recover()`；
2. `cycle()` 中在 `checkActive()` 后追加 `checkHeartbeats()`，并写 `heartbeats/butler.json`；
3. 新增 `recover(dead)`：原地重启（带 resume）→ 失败则 `promote(standby)` + `spawnStandby()`（见 2.4 伪代码）；
4. `dispatch()` 中记录 `sessionId` 到心跳（spawn 后从 RPC/stdout 捕获 session id）；
5. org.json schema：节点增加 `twinPool`、实例增加 `role: primary|standby` 字段；registry.js 加对应读写。

### 4.3 spawn.js 改动点清单

1. pi 分支增加 `--resume <sessionId>` 参数透传（**前置验证项**：确认 pi CLI 在 rpc 模式下 resume 的行为，见分歧点 D6）；
2. 可选：spawn 成功后把 pid + sessionDir 写入初始心跳。

### 4.4 接管流程交付物

- `logs/ha.log`：全部 HA 事件（掉线判定/重启/转正/补位）审计流水；
- 接管摘要文件：`agents/twin/tasks/handover-<date>.md`（转正者写给用户的现场摘要）；
- 面板展示（可选）：web 状态板加"心跳年龄"列。

### 4.5 实施顺序建议

1. 心跳写入 + butler 巡检只读不救（观察一周误报率）→
2. 开原地重启（resume）→
3. 开备用池转正 →
4. OS 看门狗兜 butler。

## 5. 分歧点（留给用户裁决）

| # | 分歧 | 选项 | 分身倾向 |
|---|---|---|---|
| D1 | 备用池大小 | 1 个 / 2 个 | 1 个起步（备用的意义是兜底不是并发，多了纯占位） |
| D2 | 备用实例的模型渠道 | 与主分身同渠道 / 便宜渠道待命 | 平时不启动=零成本，转正时用主分身同渠道即可，不另设 |
| D3 | butler 看门狗形式 | 任务计划程序 / 守护版 VBS 循环 / 主分身反盯 butler | 任务计划程序为主 + 主分身反盯为辅（双保险，成本≈0） |
| D4 | 心跳超时阈值 | 60s / 90s / 120s | 90s + 防抖一轮（=最坏 ~3 分钟判死，夜间模型排队不误杀） |
| D5 | 主分身窗口掉线时，是否自动弹窗/推送告知用户 | 静默接管等用户开口 / 主动推送 | 主动留摘要到固定位置 + 用户下次开口第一句汇报（不打扰原则） |
| D6 | 技术验证项：pi rpc 模式 `--resume` 是否可靠恢复上下文 | 需实测 | 实装前必须先跑一次最小验证（丢上下文则降级为文件系统重建） |

## 附：与用户原话的对应

- "1号干活时定期看2号" → 改为：1号只写心跳，看人的活归 butler（省掉监工税）；
