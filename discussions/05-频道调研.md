## 二、加「虚无」频道的三个方案

### 方案 A：HK 恢复后，加一个「虚无观察员」topic-agent（贴合现有架构）
- 做法：仿照 8/2 扩频道的模式，在 `chat_room_topic_agents` 加一条记录 +
  新增一个数据源。但现有频道都是"抓外部平台热搜"，虚无频道的话题源得自定义——
  可指向 org 框架的公开产出（如 web 面板的 /api/state 摘要、discussions/ 新稿、inbox 完成摘要）
  做一个小 HTTP 端点供 new-api 抓取，观察员每小时把"框架今天干了什么"带进聊天室讨论。
- 利：完全复用现有机制（轮询/串门/展示），用户在熟悉的聊天室里旁观框架动态；改动集中在
  已验证过的代码路径（`fetchChatRoomHotTopicsForSource` 加一个 case）。
- 弊：需改 Go 源码 + 重新编译部署（140MB 二进制）；话题源端点要么暴露 org 状态
  （需鉴权/脱敏设计），要么人工维护一个摘要文件；**前置依赖 HK 恢复**。

### 方案 B：把频道搬/镜像到 US 或本地（不推荐现在做）
- 聊天室功能编译在 new-api 二进制里，US 的 sub2api 是另一个产品，没有这套表。
  要在 US 跑等于再部署一套 new-api，与现有 HK 单点实例分裂（两个聊天室、两份历史）。
- 弊大于利，仅作为 HK 长期不恢复时的备选。

### 方案 C：纯 org 侧实现「旁观频道」（轻量替代）
- org web 面板已有分身/管家对话（`/api/chat/<id>` + history.jsonl）和 discussions/ 讨论稿，
  用户本来就能旁观。可再加一个只读"讨论流"页签聚合 discussions/ + butler.log 决策行。
- 利：零外部依赖、不碰生产服务、随时可做；弊：不在用户熟悉的聊天室里，"旁观感"弱于 A。

## 三、利弊汇总与建议

| | A（HK new-api 频道） | B（US 新建） | C（org 内置旁观页） |
|---|---|---|---|
| 用户旁观体验 | ★★★（熟悉场景） | ★★★ | ★★ |
| 工作量 | 中（源码+编译+部署） | 大 | 小 |
| 风险 | 动生产服务（有 8/2 备份回滚经验） | 架构分裂 | 无 |
| 前置条件 | **HK 恢复** | HK 持续故障 | 无 |

**管家建议**（待分身/用户裁决）：
1. 分身倾向加——认同其理由（异步讨论透明化，符合用户"透明管家"偏好）。

3. 建议顺序：**先修 HK**（可单独立任务）→ 修好后按方案 A 实施（话题源用脱敏的框架动态摘要端点）；
   期间若用户想立刻有旁观渠道，顺手做方案 C 的只读聚合页作为过渡。

   只输出脱敏的任务摘要。
